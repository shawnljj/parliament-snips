Notes on a small project

Reading a day of Parliament in forty minutes

Singapore publishes everything Parliament says. That is 70,796 words for a single sitting — roughly 7.9 hours of reading, if you have the day free. Parsnips turns it into a page you can finish over coffee, where every claim still points at the sentence it came from.

Why bother

A sitting covers Bills, ministerial statements, oral answers and Budget debates, and the record of it is genuinely good. It is also unusable for anyone who is not a lawyer or a political scientist. News coverage swings the other way and gives you a phrase, chosen for how it reads rather than for what was decided.

What I wanted was the thing in between: enough to understand what the government is actually doing, without pretending to be the transcript. The target I set was deliberately blunt — a sitting should take 30 to 60 minutes to read. That turns a vague ambition into a number I can work against, and it turns into roughly 10 seconds per speaker once you divide it up. Every summary the system writes has to fit that budget.

What a page looks like

Every exchange gets a short brief, in the order it happened. Not a highlights reel — the whole sitting, just compressed. Each brief carries a few points, and each point carries the words it was taken from, one tap away.

An example, from 2026-01-12

“The PSGA was introduced in 2018 to enable public agencies to share data safely and purposefully.”

Said by Ms Jasmin Lau, and shown with this underneath it: “It helped to enable, among other objectives, public agencies to share data safely and purposefully, so that we can serve Singaporeans better.”

The quote is not a paraphrase. It is the sentence from Hansard, and the system is built so that it cannot be anything else. That constraint is the most interesting thing about the project, so the next section is about it.

The one idea that makes it work

Most summarisers ask a model to read the text and write out the quotes. That is where things go wrong quietly: the model reword a sentence slightly, and unless you check every quotation against the original you will never notice. So I stopped asking.

The model never writes a quotation. It points at one — it returns the id of the sentence it is talking about, and the system pastes the real sentence in afterwards. The model can be wrong about which sentence matters. It cannot invent one.

Which means the claim below is checkable by anyone, including you. Try it.

How it fits together

Four steps, and only one of them uses a model. Everything mechanical — fetching, cleaning, counting, pasting quotes back in — is ordinary code, which is both cheaper and repeatable.

  1. Fetchno model

    Pull the sittings down and keep them, exactly as published.

    One batch per year, resumable, so an interrupted run picks up where it stopped. 331 sittings, no failures.

  2. Break it upno model

    Cut each sitting into the units a reader thinks in.

    A sitting becomes sections (Bills, statements, oral answers), each section becomes one speaker's turn, and each turn gets its own id. Every sentence is numbered so it can be pointed at later.

  3. Summarisemodel

    Read a turn and decide what mattered.

    The only step that needs judgement, so it is the only step that uses a model. Large items — 880 of 3,912 — are handled in pieces.

  4. Checkno model

    Prove it before it goes out.

    Every quote is re-checked against the archive, and so is the coverage: how much of the item actually got summarised. Anything that fails is held back rather than published with a caveat.

The check is two questions, not one, and that turned out to matter. The first is “does this quote exist in the record”, which sounds like enough. The second is “did we actually summarise the whole thing”. I only added the second after the first one spent a while telling me everything was fine while it wasn't.

Chunks are lists of ids, not slices of text, which is what keeps the whole thing checkable. excluded_counts records what was left out and why, so a silent drop is impossible. The turn_index on each sentence counts the turns that survived filtering, across the whole item — not the sitting's array positions — which is exactly the kind of thing that has to be written down, because I got it wrong the first time and cited a turn number the pipeline would never produce.

Things that went wrong

Worth writing down, because they changed how the thing is built rather than just being bugs I fixed.

  1. The check that said 100% while the output was empty

    A rule meant to skip procedural noise was matching in the wrong place, and throwing away whole ministerial speeches — 742 turns across the archive carry that flag, including one 6,403-word reply.

    The lesson: my quote checker was reporting a clean bill of health the entire time. It could not see the problem, because a summary with nothing in it trivially has no wrong quotes. A check that only tests one way of being wrong will happily certify a different failure. That is why coverage is now checked as well.

  2. A document of mine was wrong by 16×

    I had written “1,100,000 words per sitting” in my own notes. The real figure is 70,796. Nobody had recomputed it, because it was written in prose rather than produced by the code.

    So now anything the system says about itself is computed from the data, and this page is built the same way — the numbers you are reading were generated from the archive when the page was built, not typed by me.

  3. Being clever about selection was the wrong instinct

    My first design had code pick the important sentences and gave the model only those, which felt efficient and responsible. It was a trap: if the code chooses badly, the model never sees the rest and writes a confident summary of the wrong material anyway.

    Deterministic code is good at the boring parts — cleaning, filtering, pasting quotes back. Deciding what matters is the part it is bad at, and the part a model is good at. Splitting the work along that line is the whole architecture.

Where it stands

In progress, and built one step at a time on purpose. The archive is done and the summarising step is next; I would rather show you where the line actually is than round it up.
